# 把插件变成能安全拆装的乐高：《时空可组合性编程范式》通俗解读

## 一、这篇论文在回答一个你每天都在经历的问题

2026 年 8 月 13 日，DeepSeek 开源了 DeepSeek Harness，并同步公开了一篇 88 页的论文《A Programming Paradigm for Spatiotemporal Composability》，中文可译为《一套处理时空可组合性的编程范式》，作者来自北京大学和 DeepSeek AI。论文很长、符号很多，但问题很简单：软件世界里的“零件”，能不能像电源插头一样，随时插上、随时拔掉，拔掉之后还不留任何痕迹？

这就是“动态组合”：组件在运行过程中被加载、卸载、替换，而系统继续正常工作。插件、App、智能体（Agent）都依赖这件事。可现实是，大部分软件做不到。论文统计了 Visual Studio Code 安装量前一百的扩展：八十七个含可执行代码，而这些扩展几乎都无法在不重启整个编辑器的情况下被单独卸载。一个扩展把编辑器“污染”了，你要关掉整栋楼，才能修好一间房。

我们普通人当然不写插件。但“装上容易、拆下难”“改了一个地方，别的地方跟着崩”“两个人互相等着对方先动手”这些烦恼，在生活里随处可见。这篇论文的有意思之处，就是它把这类问题拆成两个可操作的维度，并给出了一套理论上可验证、工程上已落地的解法。下面我们不碰一个公式，把它讲清楚。

为什么这个话题值得你现在就关心？因为身边几乎每样东西都在长“插件”：浏览器的扩展、手机里的快捷指令、桌面软件的插件市场，再到 AI 智能体里随时加载的技能、工具和记忆。东西越多，越需要一套统一规矩：装进去能干活，拆下来不残留。这篇论文第一次把这条规矩写成可验证的软件理论，并交出一份能直接运行的工程实现。

**速览**：这篇论文用两个维度把“动态组合”讲清楚——时间可组合性管“拆得干净”，空间可组合性管“接得聪明”；解法是给每个动作配一个逆操作，让依赖关系变成活的声明；工程落地是 Cordis，最大规模验证是 Koishi 的 4000 多个插件，最新舞台是 DeepSeek Harness。全文不碰公式，只看它如何变成可复用的生活智慧。

## 二、两个关键词：时间可组合性与空间可组合性

论文把“动态组合”拆成两个互不依赖的维度。

第一个叫“时间可组合性”：一个组件被移除时，它之前对共享环境做的所有改动——注册的服务、监听的事件、占用的资源、改掉的配置——必须被完整、安全地撤销。重点不是“删掉这个文件”，而是“把环境恢复成它没来之前的样子”。

第二个叫“空间可组合性”：组件之间要能声明依赖、发现依赖、响应依赖变化。A 需要 B 提供的服务，那么 B 出现时 A 自动启动，B 消失时 A 自动停机，B 被换成 C 时 A 自动重连。依赖关系不是写死的，而是“活的”。

生活类比：时间可组合性，相当于合租室友搬走时把公共区域恢复原状，而不是留下一堆自己的东西；空间可组合性，相当于你的设备声明“我需要 HDMI 接口”，接口插上就能用，拔掉就休眠，换一个接口也能立刻用。

过去几十年的软件，主要靠两招对付这两个问题：一是词法作用域，代码块结束就自动清理，像函数返回后局部变量消失；二是依赖注入，启动时把依赖接好，像开灯前先把电线拉好。这两招都只适用于“装好就不动”的静态世界。插件是运行时才来的，依赖是运行中才变的，于是所有“清理”都退化成手动操作，靠自觉、靠文档，最后常常漏掉。

打个比方：词法作用域像一次性餐盒，吃完一扔不用收拾；依赖注入像装修前把水电管线一次性排好。但插件世界是合租公寓：家具随时搬进搬出，公共区域要反复收拾，新室友还可能换掉旧家电。静态世界的工具，天生管不了动态世界的脏活。

## 三、以前为什么做不到：两个真实案例

论文拿 Visual Studio Code 当反面教材。它的扩展宿主是一个共享进程：扩展可以动态安装，却无法单独卸载。所谓停用钩子，只是在宿主进程退出前打个招呼，不是真正的热卸载。更糟的是，清理代码和创建代码被分开写在两个地方，作者很容易忘记配对，漏掉一项就悄悄泄漏一个资源。

依赖方面更荒凉：前一百个扩展里只有七个声明了对其他非内置扩展的依赖。原因是扩展接口只向宿主开放，扩展之间没有一个结构化的契约；即使能拿到另一个扩展的导出对象，类型也几乎是“不检查”的，编译期不校验，运行期随便崩。结果就是：大家都只跟物业打交道，邻居之间互不认识，也没有协议。

而且仅有的这七个依赖大多是“同一作者自己写的配套扩展”，跨作者、跨生态的协作几乎没有——不是大家不想合作，而是接口根本没有给合作留位置。

另一个“补丁式”方案是粗粒度管理：出问题就重启整个进程，或者用容器编排管理服务。代价很大：重启会丢掉所有进程内状态，缓存、连接、跑到一半的任务全没了，重建要几秒到几分钟；容器之间通信有额外开销，而且容器管不到共享同一进程内存的细粒度依赖。论文的批评很直接：现代系统在“比进程更细”的粒度上组合，管理工具却停在“比进程更粗”的粒度上。

把代价翻译成人话：你正在用的编辑器里，某个扩展卸载不干净导致菜单错乱，唯一办法是关掉整个应用、重新打开、再找回刚才没保存的思路；换成服务器场景，一个模块升级失败，可能要把整组服务一起重启，所有在线用户被踢下线。论文统计里的“八十七个”真正在意的不是数字，而是“几乎每个扩展都会污染宿主”这件事本身：既然大多数扩展都会留下痕迹，靠作者自觉清理就注定不可靠。

## 四、核心解法：可逆副作用加反应式依赖

论文把两个古老的理论概念——“效应”和“余效应”——从“编译期检查”改造成“运行时机制”。

可逆副作用：不再要求整个系统可逆，只要求每一个原子操作自带“逆操作”。你做一件事的同时，把“怎么撤销这件事”交给运行时。运行时把逆操作按后进先出顺序串成一条撤销链；卸载组件时，只要把整条链跑完，环境就回到组件来之前的状态。组合天然保持：两个可逆操作合成的大操作，逆操作就是各自逆操作的倒序组合。开发者只需要为每个最小操作写一次撤销，复杂的清理逻辑由系统推导出来，不需要为每个插件写一份卸载说明书。

生活里这就是“记账式管理”：每次改动都记一笔“如何还回去”，出问题时按倒序回放。它不要求你记性多好，只要求系统坚持记账。

举个具体的倒序例子：你装修刷墙，顺序是“补洞、刮腻子、刷底漆、刷面漆”。想还原到毛坯，不能从面漆开始“继续刷”，而要倒着来：先铲面漆，再磨底漆，再铲腻子，最后回到补洞之前。每道工序的逆操作只跟它自己那一步有关，但合在一起，就构成一条能完整回家的路。运行时做的事，就是把这条“回家路线”替你记下来。

反应式依赖：组件在出生时就交两份清单——“我需要什么”和“我能提供什么”。运行时把共享环境做成一张依赖表：有人提供、有人消费。每当依赖表变化，系统就把每个组件分类成三种：激活，我需要的都齐了；停用，我需要的缺了；无关，与我无关。然后自动驱动启动、停机或重载。

生活里这就是“声明需求，别偷偷伸手”：打印机声明“我需要驱动”，驱动装好打印机才就绪；驱动被卸载，打印机先进入休眠而不是报错崩溃。关键细节是顺序：提供者要离开时，先通知所有依赖方撤退，等它们全部完成善后，提供者才开始拆自己。先让房客搬走，再拆房子。

隔离与拦截也有生活版：同一本菜谱，给小孩看用“无火版本”，给大人看用“明火版本”，菜谱还是那本，场景不同解析就不同；拦截像是门卫多问一句“你进去做什么”，不改变你这个人，却改变了你能碰到的范围。

论文还补了两个精细机制。一是“隔离”：同一个依赖名字，在不同上下文里可以解析到完全不同的实例。多租户、测试环境、给不同用户不同配置，都靠它，就像同一把钥匙在不同楼层开不同的门。二是“拦截”：依赖被访问时，系统可以附加权限元数据，比如“这个组件只能读数据库、不能写”，而且不用改组件本身，就像门禁卡上盖了个章：进门可以，进保险库不行。

## 五、一个关键哲学：撤销到“观察等价”就够了

这里有个容易被误解的点：所谓“恢复原状”，并不是物理上回到过去。论文明确说，物理状态不可能原样恢复：释放内存后，堆的布局不会变回申请之前；删掉的临时文件，磁盘扇区也不会倒带。真正要求的是“观察等价”：任何观察者用系统提供的操作来检测，都分不清“撤销后”和“从未发生过”的区别。你在外面吃饭，结账后退款，业务记录可以做到像没消费过一样——哪怕底层日志里还留着痕迹，只要业务接口上一致就行。

验收标准也随之改变：不是“翻旧账找出所有痕迹”，而是“用对外接口测一遍，行为一致就算成功”。这给修复设了一个可以落地的终点，而不是一个永远够不着的完美目标。

这个“对外等价即可”的哲学很有生活智慧：修复不等于时光倒流。东西弄坏了，道歉、赔偿、替换，只要双方在约定接口上达到一致，关系就可以继续。要求“完全一模一样”常常是执念，也是许多修复工程失败的原因——他们追求不可达的完美还原，而不是可验证的等价恢复。

更进一步，论文区分了“系统边界内”和“系统边界外”。边界内，也就是自己独占的资源，比如私有临时文件、自己的内存，可以真正撤销；边界外，也就是已经发给别人的数据、已经打出去的电话，无法撤回，只能用“补偿”处理：删掉你创建的文件、退还你扣掉的钱。补偿也遵循同样的顺序化组合。这告诉我们：承诺要分“可撤销”和“不可撤销”两类；对不可撤销的部分，要么延迟发送直到确定，要么提前准备好补偿方案。

边界外的典型是“已经发出去的消息”：系统能做的不是把消息从对方手机里删掉，而是再发一条更正、撤回权限或补一份说明。商业世界也一样，扣错钱可以退款，公开声明却只能澄清。认清边界，才不会把力气花在“撤回”上，而是花在“善后”上。

## 六、从局部到全局：组件、纤维与状态机

单个机制成立还不够，论文的野心是把保证从“一个组件”带到“整个系统”。它把“组件”作为基本单位：一个组件等于需要什么、提供什么、做什么以及如何撤销。运行时里每个组件的一次实例化叫作“纤维”，有自己的生命周期状态机：未激活、加载中、激活、卸载中、未激活。

两个细节让这套状态机可靠。第一是“惯性”：一个加载或卸载一旦开始，必须完整执行完，才响应新的目标变化；中途目标又变了，就接着链式转换，而不是半路打断。这避免了一边卸载一边加载的竞态。第二是“先撤依赖方”：卸载开始前，先把“我不再提供了”广播出去；依赖方重新评估后各自进入卸载；提供者等到所有依赖方真正停机，才执行自己的撤销链。整个依赖图按需遍历，不需要事先分析，也不会死等。

依赖循环怎么办？A 需要 B 提供的东西，B 也需要 A 提供的东西，两个都永远无法满足。论文的结论很干净：这种情况下两个组件就是永久不激活，而且这个结论从声明就能推出，可以在加载时报错，而不是等到运行中死锁。生活对应：两个人都要求对方先写推荐信，这事在逻辑上就无解，早发现早换方案。论文还给出拆解思路：把双向交互拆成两个核心加两个整合件，每个核心只单向依赖对方，整合件负责搭桥，循环就消失了。

状态机的“惯性”也值得单独记住：它承认现实世界里没有“瞬间完成”的切换。卸载到一半收到新指令，系统不会丢下残局去追新目标，而是先把手上的动作跑完，再按新目标继续。生活里对应“先关旧灶再开新火”：换燃气灶时不会一边拆旧炉子一边点新火，而是先清场、再安装、最后点火。

## 七、落地：Cordis 元框架，四千个插件的实战验证

理论之外，论文给出了实现：Cordis，一个“元框架”。它不绑定任何业务——不管你是做聊天机器人、网页应用还是 AI 智能体，它只提供一套通用的动态组合语义：副作用追踪、依赖解析、配置协调、热替换。

它分三层。核心库提供执行并登记撤销、提供和读取依赖、实例化组件等原语。加载器让管理员用一份声明式配置描述整个系统：哪些组件、什么配置、开或关。配置变化时，加载器做“增量协调”：身份或模块换了就重建；配置内容变了交给组件自己决定是否重载；开关变了就卸载或重载；嵌套组件按标识做差量更新。不需要重启，不需要手工排列顺序，系统最终停在“按最终配置应该到达”的状态。

热模块替换是它最漂亮的应用：源码文件变了，系统先分类哪些模块可以热替换、哪些只能整体重启，再找出受影响的组件，最后事务性重载——先把旧模块备份，逐个替换；任何一个新模块加载失败，就恢复所有备份，整体回滚。整个过程不会出现“半新半旧”的中间态。这相当于换灯泡前先断电、换好再通电，换坏了还能把旧灯泡装回去。

这套机制在 Koishi 里有一个很直观的日常场景：开发者改完某个插件源码，保存文件，Cordis 自动把受影响的那几个组件热替换，聊天机器人不停机、在线连接不断开；如果新代码有语法错误，系统把旧版本原样装回去，用户根本察觉不到刚才发生过一次失败升级。

论文的实战证据来自 Koishi，一个建立在 Cordis 上的开源聊天机器人框架：四年多积累四千多个社区插件，从聊天软件适配器、数据库驱动到管理后台。独立开发者之间通常只约定一个接口名，比如“数据库”，不互相知道对方代码，却能动态组装、运行时切换数据库或重连适配器，且只有真正依赖它的插件受影响。论文承认这是单一生态、观察性证据，不是对照实验——但“存在且被大规模使用”本身已经说明机制不是纸面文章。

配套的 GitHub 生态也值得关注：Cordis 本体是 2022 年就开始维护的 TypeScript 元框架，Koishi 是跑在它上面的聊天机器人框架，GitHub 五千多星；论文仓库与 DeepSeek Harness 在同一天公开，Harness 上线一天左右已收获数万星标。社区反应很快：有人做了桌面工作台（oh-dsh-desktop）、Web 界面皮肤与侧边栏插件集（dsh-web-ui）、对话内生成式 UI（dsh-visualize），还有人维护了“DeepSeek Harness 插件精选列表”（awesome-dsh-plugin），把分散的第三方扩展收进一份目录。这说明“一切皆插件”不只是口号，而是已经有人在上面搭开放接口、做生态生意。

## 八、对 DeepSeek Harness 意味着什么

DeepSeek 的公式是 Agent 等于 Model 加 Harness：模型负责智能，Harness 负责把智能落地成行动。DeepSeek Harness 把 Harness 的每一个零件——模型适配器、工具注册表、会话、沙箱、存储、调度、界面，甚至驱动模型循环调用工具的智能体循环本身——都做成了 Cordis 插件。这不是营销口号，而是架构事实：你在配置里把某个插件换掉，框架会自动撤销旧插件的全部影响，等新插件的依赖就绪后再平滑启动。

需要提醒的是它仍处于开发者预览（v0.1）：官方明说接口会快速迭代、存在破坏性变更，现在上手更像“参与早期生态”，而不是“买一张长期稳定的船票”。

最值得注意的差异是“创造模式”：智能体可以检查自己正在运行的插件环境、在内存里试验新插件、甚至现场给自己造一个插件并挂到运行中的流程里。用那个流传很广的比喻：智能体发现自己没有扳手，就现场造了一把扳手，插到自己手上继续干活。传统智能体是“成品家具”，核心逻辑写死在代码里；Harness 是“生成内核”，连骨架都是可拆卸的零件。

官方把运行模式做成四种预设：标准、极简、PTC 和创造。极简模式只保留最少工具，适合跑评测、排除框架干扰；创造模式则开放“运行时体检”：查看当前系统挂了多少插件、依赖怎么连、在内存里试装新插件，甚至让智能体帮你组合出全新的运行模式。换句话说，它不给你一把锁死的椅子，而是把椅子的图纸和零件都放在你手边。

它的会话也被设计成一份只追加的事件日志：模型看到的系统提示词、用户消息、推理、工具调用和结果、权限变化、压缩、子智能体调度，全部以事件形式落盘；下一轮模型看到的历史从日志重新推导。这意味着失败可观测、过程可审计、结果可复现，对研究者和调试者是实打实的增量。

更关键的一条设计是不变式：“模型能看到什么，日志就必须能重建什么。”任何新的模型输入，都要先登记成一种新的事件类型，再渲染进上下文。这听起来像工程洁癖，但对“会自我改装的智能体”格外重要：只有过程全程可回放，AI 给自己装上或拆掉某个零件之后，人类才说得清它为什么变成了现在这样。

但也要冷静。第三方深度对比指出，对大多数日常用户，Codex 那种“声明式插件”，几个文件加配置，已经足够；需要运行时热替换的“进程内有状态组件”其实很少。两边能做到的上限差不多，差别在“下限”和“插槽”：Cordis 把容易踩坑的撤销、依赖通知、事务回滚全部兜住，代价是学习门槛更高；而智能体循环可替换这个“物理插槽”，是其他工具目前补不上的。论文自己也把“自进化智能体框架”列为未来最值得验证的方向，而不是已经完成的成果。

有篇逐行对比 Codex 与 DSH 源码的深度分析，把这套架构总结成一句俏皮话：为了“自进化”这碟醋，DeepSeek 包了一整盘饺子——副作用跟踪、依赖通知、事务性热替换，全都是为了让 agent loop 本身可以被整体拧下来、换成另一套。饺子好不好吃另说，但这碟醋目前确实只有这里有。

## 九、可以带回日常生活的十条原则

一，凡事先想好“撤销键”。做决定、签合同、装修、订阅、组队之前，先问一句：如果这个选择要退回，怎么退、代价多大？可逆的选择值得大胆，不可逆的选择要谨慎。好系统的标志不是不出错，而是出错时有清晰的回退路径。

二，依赖要声明，不要偷偷伸手。合作前把“我需要什么、我能提供什么”摆上桌。需求没满足就硬开工，是绝大多数项目半路崩掉的原因；能自动“等条件齐了再启动”，比靠意志力撑住要可靠得多。

三，更换依赖时先通知下游。换人、换工具、换供应商，先让使用方知情、完成交接、进入可停机状态，再撤旧资源。先让房客搬走再拆房，而不是拆完房才喊房客跑。

四，记账式管理自己的“副作用”。把你改过的东西、说过的话、做过的事记下来；出问题按倒序回放。习惯就是天然的撤销链：固定流程、检查清单、事后复盘，都是在给生活装“逆操作”。

五，修复到“对外等价”即可。道歉、赔偿、替换、重做，只要双方在约定接口上一致，就可以向前走。不要用“必须和原来一模一样”绑架自己，那是不可达的完美主义。

六，区分可撤销与不可撤销，准备补偿方案。发出去的消息、已经发生的转账、公开承诺，无法撤回，只能补偿。重要的事，要么延迟到确定再发出，要么提前想好“如果错了怎么办”。

七，用隔离和最小权限保护自己。同一套规则在不同场景用不同实例；给别人授权时只给窄接口，需要时再放行。门禁卡只开该开的门，比万能钥匙安全得多。

八，大变更要事务化。搬家、迁移、发布、重组，先备份、小步替换、失败整体回滚。任何宣称“改完一定没问题”的变更，都不如一句“有问题能一键还原”可信。

九，把“声明”当成接口而不是负担。无论家庭分工、团队协作还是智能体配置，把谁提供什么、谁需要什么写清楚，能省掉大量事后扯皮。模糊的依赖关系是冲突的温床。

十，允许自己“惯性完成”。一个已经开始的动作，让它完整收尾再调整方向；频繁打断只会制造半成品和烂摊子。先卸干净旧的，再启动新的。

## 十、迁移到自己项目时的可复用清单

如果你是智能体工具的用户，这套思想同样可以落进自己的工作区。第一，会话日志只追加、不覆盖，让任何一次失败都能回放，相当于给智能体装“撤销链”。第二，把规则、技能、工具当成可插拔组件：每次新增都要写清楚它提供什么、依赖什么、删除时如何清理，而不是无限堆叠。第三，变更事务化：改配置前先备份，失败能整体还原，而不是原地修修补补。第四，依赖声明优先：让智能体明确“这个任务需要哪些文件、哪些工具、哪些权限”，缺条件就不启动。第五，周期性自省：定期检查自己身上挂了多少“插件”，哪些还在被使用，哪些已经无人依赖，及时卸载。第六，把“可观测”当默认配置：关键操作留日志、留痕迹，出了问题能倒着查，日志是让任何一次失败都能回放的撤销链。这六条不依赖任何特定产品，却恰好是这篇论文想证明的东西：复杂系统想要自由组合，必须先学会干净地拆卸。

## 十一、结语

这篇论文真正做的事，是把两件长期靠“程序员自觉”的事——卸载时清理干净、依赖变化时保持协调——变成了“运行时结构保证”。Cordis 是这套理论的工程实现，Koishi 用四千多个插件证明了它能规模化，DeepSeek Harness 则第一次把整套智能体运行时都装上了可插拔的接口。对普通人的启发甚至更大：可逆的设计、明确的依赖、先通知后拆卸、事务性回滚，这些不只是软件工程原则，也是组织协作、家庭关系和个人决策的通用智慧。下一次当你装上一个“新东西”时，不妨先问一句：它有没有撤销键？谁依赖它？拆掉它的时候，世界能不能恢复原状？
