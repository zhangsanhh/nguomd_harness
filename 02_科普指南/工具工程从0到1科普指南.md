# 工具工程：Agent 的工具工程（从 0 到 1 实战指南）

> 整理时间：2026-08-03（北京时间）。配套资料清单见同目录《工具工程参考资料100+篇.md》。本文事实性结论以官方文档与可核验链接为准，经验性判断标注为建议，不冒充事实。

## 0 结论先行

工具工程不是"给大模型接几个 API"，而是围绕"模型如何发现、选择、调用、消化工具"的一整套设计，包含四个层次：工具层（schema 与实现）、执行层（循环、错误、权限）、接入层（函数调用、MCP、注册表）、治理层（安全、评估、观测）。落地顺序只有一条：先跑通一个工具闭环，再打磨工具定义，然后补执行层，再做标准化接入，最后用评估驱动迭代。跳过任何一步，后面都会返工；先追求"少而准"，再追求"多而全"。

## 1 心智模型：工具是模型与世界的契约

大模型本身不能执行代码、访问网络、读写文件，它只能输出"调用意图"（tool call）：工具名加 JSON 参数。真正执行的是你的应用。因此工具定义（schema）是模型看到的说明书，工具返回结果是模型继续思考的上下文，工具错误是模型需要处理的反馈。Anthropic 工程博客有一个精准的说法：传统函数是"确定性系统之间的契约"，而工具是"确定性系统与不确定智能体之间的契约"。工具的"用户"是模型而不是人，这是工具工程与传统 API 工程最根本的区别。

从演进看：2022-2023 年 ReAct 与 Toolformer 证明模型可以学会调用外部工具；2023-2024 年各厂商 API 普及函数调用（Function Calling）；2024 年 11 月 Anthropic 开源 MCP，把"工具接入"标准化；2025-2026 年 MCP 官方注册表、远程 OAuth、工具检索（tool search）相继落地，工具工程从"写函数"演变成"建平台"。

为什么工具工程在 2025-2026 年成为显学？三个原因：一是模型能稳定输出结构化调用，工具选择准确率从"不可用"变成"可用"；二是工具数量从几个膨胀到几百上千个，选择、检索、安全都成了工程问题；三是 MCP 把"接入"变成商品化能力，团队竞争点从"能不能接"转向"接得好不好"。工具工程因此成为 Agent 项目的核心交付物。

传统 API 工程与工具工程的差异值得单列：传统 API 的用户是人，文档靠人读；工具的用户是模型，描述直接进上下文影响选择。传统 API 返回什么由人解析；工具返回什么会被模型当作事实。传统 API 错误由人处理；工具错误由模型决定下一步。理解这三点，就能解释后面所有最佳实践。

## 2 第一性原理：一次工具调用如何发生

无论用哪家 API，流程都是四步：

1. 定义：你提供 JSON Schema 描述工具（名称、描述、参数）；
2. 决策：模型判断该调用哪个工具，输出 tool call（工具名＋参数）；
3. 执行：你的代码校验参数并执行真实函数或外部 API；
4. 回传：把执行结果作为消息还给模型，模型继续推理或作答。

各家字段名不同，模式一致：OpenAI 返回 tool_calls（name、arguments），Anthropic 返回 tool_use（id、name、input），Gemini 返回 functionCall（name、args）。现代 API 都是"显式调用"：模型只输出调用请求，由你的代码决定是否执行、如何执行。少数框架提供"自动调用"（SDK 替你执行并回传），本质只是把四步封装起来。

以查询天气为例，工具定义：

```json
{
  "type": "function",
  "name": "get_weather",
  "description": "查询指定城市的实时天气。用户问天气且城市明确时使用；城市不明确时先向用户确认。",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string", "description": "城市名，例如 北京" }
    },
    "required": ["city"]
  }
}
```

最小 Agent 循环（伪代码）：

```python
steps = 0
while True:
    resp = client.responses.create(model=MODEL, tools=TOOLS, input=messages)
    if not resp.output_tool_calls:
        break                      # 模型不再调用工具，输出最终回答
    for call in resp.output_tool_calls:
        result = execute(call)     # 你的代码：校验 + 执行 + 异常转结构化错误
        messages.append(tool_result(call.id, result))
    steps += 1
    if steps >= MAX_STEPS:
        break                      # 兜底，防止死循环
```

回传结果也有讲究：建议统一用结构化 JSON，并带上足够判断下一步的字段。例如天气工具返回 `{"city":"北京","temp_c":32,"condition":"晴"}`，比返回一段自然语言"北京现在 32 度晴天"更容易让模型准确引用。数字保留单位、时间带时区，能显著减少误读。

验收标准四条：选对工具、参数合法、执行成功、结果能支撑后续回答。怎么判断"选对"？看模型是否在正确的时机调用、参数是否来自用户意图而不是编造；"结果能支撑"看模型是否基于真实返回值作答，而不是无视结果自说自话。

## 3 写出模型能读懂的工具：schema 实操

工具描述就是提示词，工具名就是 API 名，两者共同决定选择准确率。这一节是投入产出比最高的一步。

**命名**：动词＋对象，snake_case，按服务与资源命名空间，例如 `asana_projects_search`、`jira_search`。避免 `func1`、`do_stuff`、带版本号或缩写过度的旧接口名。命名风格（前缀还是后缀）对选择准确率有实测影响，建议用评估定，不要拍脑袋。

**描述**：写明四件事——何时用、何时不用、前置条件、返回什么。相似工具必须划清边界。对比两组描述：坏描述"天气查询工具"；好描述"查询指定城市当前实时天气；用户问'现在天气如何'时使用；历史或预报请用 forecast_weather；城市不明确时先向用户确认"。描述里可以给参数示例、枚举值与默认值，它们比抽象说明更有效。

**参数**：能枚举就枚举，能加约束就加约束；必填与可选写清楚；少用自由文本。自由文本的问题不是模型不会填，而是填了你也无法校验，出错后难以追责。金额、日期、城市这类字段尽量用格式约束或枚举。

**返回**：高信号、低噪音。不要倒整表数据，只返回完成任务所需字段；把 UUID 解析成可读名称能显著降低幻觉（Anthropic 实测：语义化 ID 明显提升检索准确率）；大结果要分页，而不是一次性倒给模型。给工具加 `response_format` 参数，让模型自己选"简洁/详细"，是实测有效的做法。

**上下文预算**：模型窗口有限，工具定义和工具结果都在抢空间。经验做法是单次工具结果控制在 1-2K token 以内，超长结果先聚合、摘要或分页；高频工具定义放最前，冷门工具检索后加载。上下文省下来的每一 token，都是成本与延迟的下降。

**数量**：少而准，5-20 个起步。优先把高频相关操作合并成一个工具（`schedule_event` 而不是 `list_users`＋`list_events`＋`create_event`）；工具重叠会让模型"选择困难"，工具过多会挤占上下文、推高成本。

**检查清单**：每个工具上线前自问——名字是否一眼能懂？描述是否说了"何时不用"？参数是否都能校验？返回是否只含完成任务所需信息？错误是否结构化？改过描述后是否跑过回归？

## 4 执行层：可靠、安全、可复盘

工具定义决定上限，执行层决定下限。以下七件事缺一不可。

**循环控制**：设置 max_steps、单步超时、并行调用上限。模型可能连续调用十几个工具，没有上限就会失控。并行调用（一次返回多个 tool call）要按依赖关系分组，不要盲目并发写操作。

超时建议分两层：单次工具执行超时（如 10-30 秒）与单轮模型等待超时（如 60 秒）；慢工具（报表、批量任务）不要同步等，改成"提交任务＋查询进度"的异步工具。

**错误结构化**：工具失败返回 `{status:"error", code, message, retryable}`，不要裸抛堆栈。`retryable=true` 表示可重试（如限流、超时），模型可以自动重试；`retryable=false` 表示业务错误（如参数非法），重试无意义。重试策略用指数退避加抖动，避免同步风暴。

**结果治理**：大结果截断、压缩或缓存；回传前按 schema 校验，并检查敏感字段——邮箱、密钥、手机号禁止回传。必要时给每次执行生成"执行凭证"（tool receipts），让模型声称的结果与真实执行记录可对账。

**权限分级**：只读、写、高危三档；写与高危操作默认人工审批（Human-in-the-loop），不可信代码在沙箱中执行。审批流程要简单：展示"要做什么、影响什么、能否回滚"，而不是让用户看一堆日志。

审批流程建议四步：模型提交请求（工具名＋参数＋理由）→ 系统展示影响面（读写对象、是否可回滚）→ 用户批准或拒绝 → 结果回传模型。拒绝时把原因作为结构化结果回传，模型才知道换路。

**幂等与审计**：写操作带幂等键防重复；全链路记录"输入→选择→执行→结果"。建议每个工具至少记录：调用时间、会话 ID、模型与版本、入参、出参摘要、耗时、错误码、是否重试、是否人工审批。这些字段既是复盘材料，也是评估集的真实样本。

**安全**：工具描述可能被投毒（MCP Tool Poisoning），工具输出可能携带间接提示注入，OWASP Agentic Top 10 把"工具滥用"列为顶级风险。对策：只信任可信来源、执行前校验输入、隔离工具输出、最小权限、高危操作人工审批。

**工具路由**：工具超过几十个后，不要让模型每次看到全部定义。三种做法：按任务分组路由（先分类再给对应工具集）、向量检索（Tool RAG，把工具描述做成索引）、平台级工具检索（tool search，按需加载 schema）。

## 5 从函数调用到工具平台：MCP

MCP（Model Context Protocol）是开放协议：一个 MCP 服务器以 JSON-RPC 暴露 tools（工具）、resources（资源）、prompts（提示模板），任何支持 MCP 的客户端（Claude Code、GitHub Copilot、Codex、Cursor 等）都能直接使用。规范已迭代至 2025-06-18 与 2025-11-25 版本，配套官方 Registry（服务器注册表）、远程服务器 OAuth 与 MCP Inspector（调试器）。

三个原语各有用途：tools 是给模型执行的函数；resources 是给模型读取的数据（如文件、数据库记录）；prompts 是给用户或模型使用的模板。绝大多数场景先做 tools，需要读上下文再补 resources。传输上，本地开发用 stdio，远程服务用 Streamable HTTP，跨网络要配 OAuth 鉴权。

什么时候上 MCP：同一套工具要被多个客户端或团队复用、要跨语言、要发布给外部使用时。决策参考：工具只在自己应用里用，函数调用直传即可；要在 3 个以上客户端或项目复用，上 MCP；要对外发布或商业化，MCP 加官方 Registry；只是内部原型，都不必上。

动手路径：

1. 写服务：`pip install mcp`，用官方 Python/TypeScript SDK 或模板写一个 server；
2. 本地调试：`npx @modelcontextprotocol/inspector` 连接服务器，逐个调用工具；
3. 接入客户端：Claude Code 用 `claude mcp add <name> <command>`，其他客户端在配置中加入 server；
4. 存量 API：用 OpenAPI-MCP 一类工具把 OpenAPI 3.x 自动转换为 MCP 工具，几分钟获得可调用的服务；
5. 规模化：工具超过 30-50 个时启用工具检索与延迟加载，避免全部塞进上下文。

一个最小 Python 示例（FastMCP 风格）：

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("demo")

@mcp.tool()
def get_weather(city: str) -> str:
    """查询指定城市实时天气；城市不明确时先向用户确认。"""
    return weather_api(city)  # 换成你的实现

if __name__ == "__main__":
    mcp.run()
```

写完先跑 Inspector 验证，再接客户端实测"模型能否正确选择与传参"——MCP 只是传输层，工具描述质量决定它好不好用。

MCP 安全不能靠协议保证，官方规范明确要求宿主做授权与控制。上线前过四关：服务器只从可信来源安装并审源码；工具执行前做输入校验（类型、长度、嵌套深度）；敏感操作按权限分级并记录；工具输出隔离，防止返回内容里夹带指令（间接提示注入）。

如果要把工具发布给他人：按官方 Registry 规范提供 server 信息（名称、描述、命令或 URL、权限声明），先本地验证再发布；远程服务器必须支持 OAuth 或 API Key 鉴权，并在描述里写清数据用途。

## 6 框架选型：一句话判断

OpenAI Agents SDK：托管工具（web search、file search、computer use）与函数工具，快速起步；LangGraph：需要图式编排、中断与人工审批；LlamaIndex：RAG 与文档类工具；CrewAI：多角色分工；Pydantic AI：类型安全与结构化输出；Spring AI / LangChain4j：Java 生态；AutoGen / AG2：多智能体研究；Semantic Kernel：.NET。选型标准不是"哪个火"，而是模型无关性、工具调试体验、可观测性、团队语言。原型阶段可以不用框架，直接写 while 循环，跑通后再迁移；框架帮你省的是样板代码，不省工具设计。

团队常问要不要多框架混用。结论是尽量单一框架：工具层做成独立模块，通过统一网关（如 LiteLLM 一类 OpenAI 兼容网关）或 MCP 暴露给多个 Agent，而不是每个框架各写一套工具。工具定义、实现、测试只维护一份，才能保证行为一致。

## 7 评估：没有测试就不算完成

**指标**：工具选择准确率（该调用时调用、选对工具）、参数准确率（参数值来自用户意图且合法）、任务成功率（端到端目标达成）、错误恢复率（失败后能否自愈）、幻觉率（编造工具、参数或结果）、成本与延迟。

**基准**：BFCL（函数调用综合榜）、τ-bench（工具-用户多轮）、ToolBench / API-Bank（大规模 API）、AgentBench / OSWorld（环境与电脑操作）。平台内可用 EvalScope、LangSmith Trajectory Evals、Anthropic 工具评估 Cookbook。

**落地方法**：先写 20-50 条贴近真实业务的任务（多轮、多工具），固定"提示词＋工具集＋模型"作为基线；每次改动工具描述、参数或执行逻辑都跑一遍回归；线上抽样标注失败轨迹，形成迭代闭环。评测分三层：单元层（单工具调用对错）、轨迹层（多步调用顺序与中间状态）、端到端层（最终结果是否满足用户目标）。任务要贴近真实复杂度——一次任务可能调用十几个工具；验证器不要过严，别把合理的格式差异判为错误。

指标要可计算：选择准确率＝正确调用次数÷应调用次数；参数准确率＝参数完全合法且来自用户意图的调用数÷总调用数；任务成功率＝达成目标的测试任务数÷总任务数；幻觉率＝编造工具、参数或结果的次数÷总调用次数。先定分母，再谈优化。

一条评测任务建议包含：用户原始请求、可用工具集（含版本）、期望路径（可有多条）、最终验收条件、禁止行为（如不得调用写接口）。这样既能算准确率，也能防止模型走捷径。

## 8 六个高频坑

1. 描述含糊：模型选错工具或编造参数——把描述当提示词逐字打磨，相似工具显式划界；
2. 工具爆炸：几十个工具全塞上下文，选择退化、成本上升——分组路由、向量检索、按需加载；
3. 死循环：模型反复调用同一工具或空转——max_steps、重复调用检测、行为熔断；
4. 参数不校验：越权、破坏数据——执行前 schema 校验加权限检查，写操作幂等；
5. 结果不验证：幻觉顺着工具结果扩散——回传前校验，必要时给执行凭证；
6. 不观测：出了问题无法复盘——每次调用留 trace 与日志，定期抽样标注。

还有一个隐藏坑：改工具不通知模型。工具实现变了、描述没变，模型按旧理解调用，问题最隐蔽。工具变更要版本化，描述、实现、评估集三者同步。

## 9 30 天落地路线图

第 1 周：跑通 1 个工具闭环，选 3-5 个高频工具，验证四条验收标准。每天只做一件事：定义 1 个工具、跑通、写 3 条用例。
第 2 周：打磨 schema 与返回结构，建 20-50 条评估集，记录基线。每改一个描述，跑一遍基线对比。
第 3 周：补执行层（超时、重试、权限、人工审批），把 1 个服务 MCP 化并接入客户端。先只读，再写，最后高危。
第 4 周：接观测与评估流水线，跑回归、修工具、定发布与回滚流程。发布门禁：评估通过＋写操作有人审＋trace 可查。

建议固定节奏：早上跑一次基线回归，下午改一个工具并记录改动，晚上看 10 条失败轨迹写原因。四天一个小迭代，一周一次评审，避免把问题攒到最后。

四周边界要提前约定：第 1 周结束标准是至少 3 个工具通过验收；第 2 周结束是评估集跑通且基线可复现；第 3 周结束是 MCP 服务被至少 2 个客户端调用成功；第 4 周结束是发布门禁生效。任何一个里程碑没到，先停增量、回去修工具定义，而不是继续加工具。

验收标准：任务成功率可量化、工具错误可追溯、写操作有人审、模型选择准确率不低于基线；每次发布前跑一遍回归集。

## 10 一句话总结
