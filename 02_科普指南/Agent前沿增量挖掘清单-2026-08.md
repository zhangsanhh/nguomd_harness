## 0. 维护规则（可拓展性 / 可移植性）

1. **状态机**：`📋未挖` → `🔍跟踪中` → `✅已核验` → `🛠已落地` / `❌已否`。每条模块只更新「状态、日期、依据」，不重写历史。
2. **新增模块**：复制第 3 节模板，分配 M-xx 编号，在总表加一行；挖完即更新状态，不积累死条目。
3. **查重闸门**：新增前先 `rg` 检索全项目（含 02_科普指南、提示词库、会话日志与摘要），命中已有内容则只补差异、不建新条目。
4. **可移植性**：本文件自包含，引用只用相对路径或完整 URL，不依赖本工作区绝对路径；迁移到其他项目时整文件复制，只改「适用环境」一节。
5. **来源纪律**：官方一手 > 权威媒体 > 一般网络；每条关键来源带日期；官方页面直连失败时按 Pitfall-005 换官方检索取证。
6. **挖掘前提（2026-08-04 用户矫正，适用于后续所有模块）**：
   - 抗内化：增量优先落在规则层/状态层/接口层（模型无法内化淘汰）；记忆、技能、自动总结等会被模型能力吸收的机制一律降权为「仅参考」。
   - 低嵌入成本：默认不增加 token 与等待；确需嵌入时必须给出精确成本，并写明用户日常任务中可见的提升点，收益须明确大于风险。
   - 分级输出：每个模块核验后按「值得嵌入 / 仅参考 / 已淘汰」三档标注，禁止只报机制不报成本收益。

## 2. 模块详情

### M-01 Hermes Agent（Nous Research）机制核验与跟踪

- 现状/差异：全项目零覆盖；Hermes Agent 是 Nous Research 开源（MIT）的自进化 Agent（hermes-agent），与列表内其他「编码 Agent」不同，属长驻型 agent harness：CLI + Telegram/Discord/Slack/WhatsApp/Signal/Email 单网关、cron 自动化、本地/Docker/SSH/Singularity/Modal/Daytona/Vercel Sandbox 七种终端后端；最新 v0.19.1（2026-07-30）。
- 为什么值得挖：Arize 架构拆解认定它是当前开源 harness 中最完整参照之一（九组件全实现），且与用户 Codex 配置直接可比的机制很多：记忆双轨（MEMORY.md/USER.md）、血缘式压缩、工具注册与暴露分离、系统提示词三层组装、双面 hook、provider 适配层（含 Codex Responses/app-server 路径）。
- 已核验结论（2026-08-04，官方 docs 直连抓取；标注「第三方/待核验」的除外）：
  1. 记忆闭环：built-in 双轨 MEMORY.md/USER.md ＋ 8 个外部记忆提供方（Honcho/Mem0/OpenViking/Hindsight/Holographic/RetainDB/ByteRover/Supermemory，同时仅 1 个 active，built-in 始终并存）。Honcho 是 AI-native 记忆后端，核心是三层注入（base context ＋ dialectic supplement）与三个正交旋钮（contextCadence/dialecticCadence/dialecticDepth）、recallMode 三档（hybrid/context/tools）、五工具（profile/search/context/reasoning/conclude）、sessionStrategy 四档（per-directory/per-repo/per-session/global）、多 profile 多 peer 隔离——对照用户 memories=true 黑盒，这是唯一能拆解「记忆怎么存、怎么召回」的开源实现。
  2. 血缘压缩：压缩不是改写 transcript，而是 aux 模型总结旧轮次后关旧会话、开子会话、记录 parent-child lineage、轮换 session ID；head/tail token budget 保护，tool outputs 旧于阈值先剪再总结，summary budget 约压缩内容 20%（floor 2k/ceiling 12k）——与 Codex auto_compact 直接改写 transcript、无血缘形成机制差异（第三方：Arize 2026-06-01；官方 compression-eval 2026-05-15）。
  3. 安全模型：8 层防御；v0.19.0 起 smart approvals 默认（aux LLM 评估，低风险自动批、危险自动拒、不确定转人工，300s fail-closed，cron deny 默认）；Hardline Blocklist 永不被 --yolo/off 绕过；user deny rules 先于 yolo 生效；AGENTS.md/CLAUDE.md/.cursorrules 加载前做注入扫描；写盘 denylist 含 ~/.ssh、~/.aws、~/.kube、.env——可直接对照用户 PreToolUse 闸门/Guardian 与 hooks。
  4. Skills：兼容 agentskills.io；渐进披露三级（L0 skills_list 约 3k tokens → L1 view → L2 view＋path）；/learn 把经历/目录/URL 转 SKILL.md；Skill Bundles YAML 一条命令加载多技能；条件激活字段（fallback_for_toolsets/requires_toolsets/fallback_for_tools/requires_tools）与 platforms 字段；GitHub/URL 安装进 quarantine 并记 lock.json（source URL/content hash/scanner version/timestamp）。
  5. DeepSeek/Codex 链路：DeepSeek 官方文档已有 Hermes 接入页（Quick Setup 选 DeepSeek、deepseek-v4-pro；直连被 SSRF 拦截、官方搜索命中，待核验）；api_mode 抽象含 codex_responses（双路径）；仓库已含 codex_app_server_session.py（一个 Hermes session 持有一个 Codex thread）；issue #24445 提议 Hermes 作控制面、Codex app-server 作 leaf delegation provider（未合并，作者 fork 实验）。
  6. 量化参考：GitHub issue #4379 报告每次 API 调用固定开销约 13,935 tokens（system prompt＋tool definitions，约 73% 固定；社区实测，待核验）；v0.19.0 冷启动 first token 约 4.3s→0.9s（官方发布说明）。
- 两前提复评（2026-08-04，按「抗内化＋低嵌入成本」过滤）：
  - 值得嵌入（运行时零 token/零等待）：硬防线规则扩充。Hermes 的 Hardline Blocklist 永不被 --yolo/off 绕过；用户 deny rules 先于审批生效；审批超时 300s fail-closed。现有 `pre_tool_use_gate.sh` 已有 5 条窄黑名单（rm 根/家目录、交互式 sudo、curl|sh、git reset --hard、git clean），Hermes 清单可补 3-4 条（mkfs.*、dd of=/dev、fork bomb 等），属纯规则、模型不可内化；可见提升点＝无人值守/高危命令场景拦截面扩大，日常任务零感知零成本。
  - 仅参考（不嵌入）：Honcho dialectic 记忆（外部服务依赖＋LLM 轮询成本，且记忆正被平台内化）；smart approvals（每轮额外 LLM 审查者调用，等待与 token 成本高）；Skills /learn 与 Bundles（Codex 已有渐进披露，learn 会被模型自学习内化）；压缩血缘（运行时零成本但提升仅在长会话回溯可见，不满足「日常可见」）；Codex app-server delegation（新控制面，嵌入成本高，仅链路参照）。
  - 结论：按两前提过滤后，Hermes 净增量收敛为「硬防线规则扩充」一项；该结论同时适用于「DeepSeek 直连 Claude Code」假想场景（Claude Code 有 PreToolUse 钩子与 permissions，机制不绑定工具）。
- 核心待挖问题：
  1. 学习闭环（自动建技能、技能自改进、/learn、/journey、Honcho 用户建模）的真实长期效果与成本
  2. 血缘式压缩（压缩即切子会话、保留 parent-child lineage）与 Codex auto_compact 的机制差异
  3. 工具注册/暴露分离对上下文预算的量化收益；与 M-03 Pi 极简策略是同向还是反向
  4. 智能审批（LLM 审查者默认评估标记命令）与用户 Codex 现有审批/Guardian 流程的可迁移点
  5. DeepSeek 接入方式与 Codex app-server 路径边界（是否原生支持待核验）
- 关键来源：[GitHub NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent)（README 2026-08-02；v0.19.1 发布说明 2026-07-30）；官方 docs：Honcho/记忆提供方/Skills/安全/Provider 接入（2026-08-04 直连抓取成功）；[DeepSeek 官方 Hermes 接入页](https://api-docs.deepseek.com/zh-cn/quick_start/agent_integrations/hermes/)（搜索命中，直连待核验）；[Arize 架构拆解](https://arize.com/blog/how-hermes-implements-open-source-agent-harness-architecture/)（2026-06-01，第三方）；[hermes-compression-eval](https://github.com/NousResearch/hermes-compression-eval)（2026-05-15）；[issue #24445](https://github.com/NousResearch/hermes-agent/issues/24445)；[issue #4379](https://github.com/NousResearch/hermes-agent/issues/4379)。
- 落地形式：已完成首轮核验；后续按需产出「Hermes vs 用户 Codex 现状」机制对照表，仅参考不切换。

### M-03 Pi 上下文经济学与扩展体系

- 现状/差异：全项目零覆盖；Pi（pi-coding-agent）是极简派代表，核心仅 read/write/edit/bash 四工具，提示词+工具定义 <1000 token，明确不内置 MCP/子代理/权限弹窗（作者论点：MCP 工具定义未开工先占 7-9% 上下文）。
- 为什么值得挖：与用户 1M 大上下文是相反策略；其 AGENTS.md 分层加载、Skills 按需加载、Extension 动态注入/RAG/长期记忆、会话树分支，是「少工具+渐进加载」的完整样本。
- 已核验结论（2026-08-04，官方 pi.dev/README 直连抓取；KDnuggets 实测标注第三方）：
  1. 现状：仓库已归 Earendil Works（Armin Ronacher 公司），RFC 0015 约定核心保持 MIT＋Fair Source 付费层＋Lefos 云平台；最新版 0.80.3（KDnuggets 2026-07-16 实测）；DeepSeek 是官方原生 provider（API key 直连）。
  2. 核心机制：四工具＋system prompt <1000 token；明确不内置 MCP/子代理/plan 模式/权限弹窗/待办/后台 bash；扩展系统＝TS 扩展（tool_call 事件、注册工具、自定义压缩、权限门）＋Skills（Agent Skills 标准、按需加载）＋SYSTEM.md 替换/追加＋Prompt Templates＋Pi Packages。
  3. 会话树：会话存 JSONL，每条带 id/parentId，单文件内多分支；/tree 原地跳转、/fork /clone；压缩有损但完整历史保留在 JSONL，可随时回看。
  4. 压缩：自动（溢出或接近上限）＋手动 /compact 可带自定义指令；策略可扩展（主题式/代码感知/换总结模型）；footer 实时显示 token/cache/成本/上下文占用。
  5. 权限：核心无内置权限系统，官方建议容器化（Gondolin/Docker/OpenShell）或扩展自建 permission gate；KDnuggets 实测 30 行内 TS 扩展可拦截工具调用并回传拒绝原因（拦截语义与项目硬防线一致，但 Pi 默认不带）。
- 核心待挖问题：
  1. 无护栏（默认 YOLO）下哪些场景真实可用
  2. Extension 每轮动态注入/过滤的实现边界
  3. 与 Codex skill/hook 体系的机制映射
- 两前提复评（2026-08-04）：
  - 实测否决（2026-08-04）：压缩前归档 transcript 暂不落地。实测：项目 117MB，交接快照仅 16K；`~/.codex/sessions` 89MB＋`archived_sessions` 53MB，单条长会话 transcript 2–24MB；若复制进项目，长期明显膨胀 git 体积，且收益仅长会话回溯时可见，不满足「日常可见提升」前提。若未来需要，归档目录放 `~/.codex`（git 之外），项目零增长。

### M-04 OpenCode build/plan 双模式与 provider 生态

- 现状/差异：全项目零覆盖；OpenCode（SST 开源，MIT）内置 build（默认，可读写执行）与 plan（只读、改文件拒绝、bash 需确认）双 Agent Tab，支持 75+ providers 与 BYOK，并有 Gemini Free/Groq/Ollama 免费路线。
- 为什么值得挖：用户的 DeepSeek 直连正是 BYOK 思路；「只读/可写双模式」是 Codex 权限配置之外的最小机制增量。
- 已核验结论（2026-08-04，官方 GitHub releases＋docs 直连抓取）：
  1. 现状：仓库已迁至 anomalyco/opencode（原 sst/opencode）；最新版 v1.18.11（2026-08-01）；已有桌面 App Beta；OpenCode Zen（按 token 付费）与 OpenCode Go（$10/月平价订阅、限 5 小时滚动 $12/周 $30/月 $60）两条官方付费路线，另有三方免费路线（Gemini Free/Groq/Ollama）。
  2. Agent 体系：内置主 Agent build（全权限）与 plan（默认 edit/bash 均为 ask）；内置子代理 general/explore/scout（scout 只读、克隆依赖仓库到托管缓存、不污染工作区）；隐藏系统 agent compaction/title/summary；Markdown/JSON 均可定义 agent，按需改 model/temperature/max steps/权限。
  3. 权限模型：每个 permission 键 allow/ask/deny 三态，支持 glob 细粒度规则、后匹配优先；deny 会把对应工具/子代理从模型可见描述里移除（省上下文＋防尝试）；external_directory 默认 ask；.env 读取默认 deny；`--auto` 只自动批准未被显式 deny 的请求，显式 deny 永不被 auto 绕过——与 Hermes 硬防线同一语义。
  4. doom_loop：同一工具调用连续重复 3 次（完全相同输入）触发提示，默认 ask——防模型卡死在失败命令上反复重试烧 token。
  5. 会话树：子会话可导航（child/parent），与 Pi 的树形历史同主题。
- 两前提复评（2026-08-04）：
  - 值得嵌入（零 token、毫秒级）：doom_loop 反循环闸门。2026-08-04 用户批准后已落地（dry-run）：新增 `.codex/doom_loop.sh`，由 `pre_tool_use_gate.sh` 黑名单通过后调用（实测 Codex 桌面版同事件只执行第一个钩子组，独立 PreToolUse 条目不生效，已合并回单组，见 Pitfall-040）；同一 shell 命令在 25s 窗口内连续完全相同 3 次时记录事件、不拦截；状态按会话隔离，日志在 `~/.codex/doom_loop`（项目零膨胀）；预留 `CODEX_DOOM_LOOP_MODE=intercept` 开关，观察无误伤后再转拦截。收益：失败重试循环不再无限烧 token/等待；属状态层，模型不可内化。与 Pitfall 库「失败应对原则」（重试要少、同路反复才需控制）形成两维度配合：纪律层＝快换路少调用，机械层＝闸门兜底止损；查重命中，不新增 Pitfall 条目。Codex 是否已有内置等价检测：本机核心二进制检索未见（仅有 HTTP 508/流重试计数）。
  - 仅参考：plan/build 双模式（Codex 已有 Plan/Default 对应）；权限矩阵与 deny 移除可见性（Codex 工具禁用配置待核验，项目用钩子近似）；external_directory 默认 ask（项目需全盘访问，不适用）；max steps（Codex 无等价配置）；scout 托管缓存（可作习惯：外部源码核验放 ~/.cache 不进 git）；Zen/Go 订阅（费用与服务，不适用）。
- 核心待挖问题：
  1. plan/build 双 Tab 的判定与切换规则
  2. provider 抽象层如何处理 API 差异（流式、参数名）
  3. 免费路线额度是否可作备用链路
- 关键来源：[GitHub anomalyco/opencode releases](https://github.com/anomalyco/opencode/releases/latest)（2026-08-01 v1.18.11，官方）；[OpenCode docs Agents](https://opencode.ai/docs/agents/) 与 [Permissions](https://opencode.ai/docs/permissions/)（2026-08-04 直连抓取）；[OpenCode Go 文档](https://opencode.ai/docs/zh-cn/go/)（2026-07，官方）；七牛整理（2026-08-03，stars/下载量，待核验）。
