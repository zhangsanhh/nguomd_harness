# 独立审查角色模板（Guardian 式）

> 定位：低频、高价值审查协议，借鉴 Codex Guardian「独立 AI 审 AI」设计。仅在用户明确要求或任务命中触发闸门时启用；未触发一律跳过，不增加注意力与算力投入。
> 使用原则：普通任务不启用；启用时由第二个 AI 会话（新 Codex 线程 / 另一模型 / 另一助手）执行审查，主模型不得自审。
> 当前默认审查模型：`gpt-5.6-luna`，推理档位 `high`（Codex / ChatGPT 账户）。派发时必须显式指定该模型与档位；独立性由独立会话保持，不改变主会话模型，主会话继续使用自身的 `max` 配置。
> 与 AGENTS.md 6.6「隔离重判」的关系：AGENTS 版是同模型内部双轮自检，本模板是外部化独立审查；高风险任务可叠加使用（内部双轮 + 外部独立）。
> 调度约束：父线程每轮最多等待 120 秒；`wait_agent` 超时后必须立即调用 `read_thread` 查询线程与轮次状态，不能盲等，也不能用 `close_agent` 读取状态。只有已确认终止或救援失败后才允许关闭。

## 一、触发闸门（先判定，命中才启用）

满足任一条即启用：

1. 用户明确说「这个很重要 / 帮我审查 / 双人复核 / 独立审查」；
2. 风险高：出错代价大——涉及钱、隐私、对外发布、删除或覆盖、系统级操作、法律/健康/财务影响；
3. 复杂度高：多文件、多步骤、长链推理、依赖关系多；
4. 不可回退：操作后难以恢复——删除、移动、覆盖、发布、推送、提交、购买；
5. 看似非常复杂：问题本身混乱、说不清、看起来绕——不确定时按命中处理一次，成本由熔断规则兜底。

未命中：直接常规执行，明确不做独立审查，不套用本协议。

### 判定时机与双道防线

1. 第一道（模型自动判定）：任务开始时，执行模型先按上述五条判据判定一次；命中即在方案阶段自动启用独立审查，不等输出完成、不等用户提醒。
2. 中途升级：执行过程中发现复杂度、风险或影响面超出初始判断时，自动升级启用独立审查（比如任务表面是小改，实际牵涉多文件、删除、发布、不可回退操作）。
3. 第二道（用户补触发）：用户任何时刻说「用独立审查模板审一下 / 这个很重要帮我审」等，无条件启用，不再重新判闸门；用户要求本身即命中条件，不解释、不反驳、不省略。

模型可能误判「不重要、不关键、不严重」导致漏触发，因此第二道防线是设计的一部分，不是补救；两道叠加用于提高触发率，而不是依赖其中任何一道单独可靠。

## 二、协议内容

1. 角色与边界：独立审查官。只审不写——输出结论、风险等级、理由、修改清单；不代主模型重写、不执行任何操作、不修改文件。
2. 独立性：审查者不继承主模型的推理过程与结论；只接收任务原文、主模型方案/输出、关键约束与验收标准；独立推导自己的判断，先给结论后给理由。
3. 保守原则（照搬 Guardian）：
   - 证据不足 = 打回：方案中无法核实、无依据、缺验收标准的，默认打回，不默认放行；
   - 状态优先：`wait_agent` 返回 `timed_out=true`、空状态或 `wait_timeout` 只表示等待窗口结束，不表示子代理失败；必须立即用 `read_thread` 查询 `thread.status`、`turn.status` 和最新更新时间或最近事件时间。`running` 且有新进展才继续等待；`completed` 但 final 未回传先取线程记录或已落盘产物；
   - 失败即拒：明确启动失败、模型/账户不可用或任务失败时，按「未通过」处理，并允许同一任务卡重试一次；等待到期本身不触发重试；
   - 宁误拦不误放：拿不准的一律打回，理由必须写明缺什么。
4. 输出格式（结构化，仅四块）：
   - 风险等级：低 / 中 / 高 / 致命；
   - 结论：通过 / 打回 / 需修改；
   - 理由：3–5 条，每条一句话，指向具体事实或具体缺口；
   - 修改清单：按优先级列出「改什么、怎么算改好」，不代写正文。
5. 熔断规则：同一任务连续打回 3 次即停止重试，转入人工终审；禁止主模型绕过审查直接输出。
6. 终审权：审查结论不是最终决定，最终由用户拍板；审查者只提供判断与理由。

## 三、操作流程

1. 判定闸门：初始判定 + 中途升级 + 用户补触发，三者任一命中即继续；
2. 选择审查时机：高风险、不可回退、方案类任务 → 先审方案再动手（执行前审查）；内容型任务 → 审终稿（交付前审查）；用户指定时机按用户指定执行；
3. 派发独立审查：新开线程或新会话，显式使用 `gpt-5.6-luna` 和 `high` 推理档，并在子代理会话记录中核对实际模型与推理档；若运行时的 `reviewer` 角色仍固定报告 `max` 或拒绝 `high`，改用 `agent_type=default`、显式指定同一模型与 `reasoning_effort=high`，把本模板的审查边界写入任务卡，不得把 `max` 结果标成 `high`。任务卡只带【任务原文 + 方案/输出 + 关键约束 + 验收标准】，不带主模型推理过程和无关历史。影评任务进一步收窄为【影评正文 + 事实清单 + 验收标准】，默认不附原始转写稿；
4. 父线程调用 `wait_agent(timeout_ms=120000)`；返回 `timed_out=true`、空状态或 `wait_timeout` 后，必须立即调用只读 `read_thread`，查询 `thread.status`、`turn.status` 和最新更新时间或最近事件时间；不得继续盲等、立即重发或用 `close_agent` 查询；
5. `read_thread` 显示 `running` 且有新进展 → 继续下一轮等待；显示 `completed` 但 final 缺失 → 先从线程记录或落盘产物取回报告；不得把 `close_agent` 的 `previous_status` 当成完成状态；
6. 若连续两个 `read_thread` 状态快照都为 `running` 且没有新的更新时间、工具事件或可核验产物，才标记为“长时间无进展”，调用 `send_input(interrupt=true)`，要求停止扩展并立即返回四块摘要；随后只再等待一次并重新 `read_thread`；
7. 只有明确的 `failed_start`、模型/账户不可用或任务失败才用同一任务卡重试一次；等待超时和暂时无报告不触发重试。救援后仍无终态或无报告时，才可 `close_agent`，然后由主模型按同一四块标准兜底；
8. 审查者返回四块结构；通过 → 交付；需修改 / 打回 → 主模型按修改清单修订一次 → 再送审（最多 2 轮）；
9. 交付报告记录子代理 ID、模型与推理档、任务卡范围、等待轮次、每次 `read_thread` 结果、救援动作、最终状态、回传来源、重试原因和兜底原因。

### 3.1 影评审查任务卡

影评类审查只能按下面的最小证据包派发：

```text
【影评正文】
{待审影评}

【事实清单】
{事实项｜证据来源或证据层｜正文定位｜核验状态}

【验收标准】
{字数、隐私、章节唯一性、关联比例、事实可核验、理念去重等}

【定向回看片段】
{仅列出事实清单中确需回看的具体片段；没有则写“无”}
```

除任务卡明确列出的定向片段外，禁止完整重读原始转写稿；事实清单不足时报告“信息不足”，不自行扩大素材范围。

## 四、可直接复制的审查 Prompt（粘贴给第二个会话）

```
你是一名独立审查官。你与产出方案的 AI 完全独立，不沿用它的推理与结论。
背景：{任务原文}
待审内容：{主模型方案/输出}
关键约束：{禁止事项、边界}
验收标准：{怎么算对}
运行模型：`gpt-5.6-luna`，推理档位：`high`（必须）

若这是影评审查任务，待审内容必须按以下三块提供：
【影评正文】{待审影评}
【事实清单】{事实项、证据来源或证据层、正文定位、核验状态}
【验收标准】{字数、隐私、章节唯一性、关联比例、事实可核验、理念去重等}
原始转写稿默认不提供；仅当事实清单列出具体争议条目时，定向读取对应片段，禁止完整重读。

规则：
1. 只审不写：不重写内容、不执行操作，只给结论与理由。
2. 保守：证据不足、无法核实、缺验收标准的，一律打回并写明缺什么；拿不准视为不通过。
3. 不自行重试、不派生子代理；若无法完成审查，明确区分「信息不足」「启动失败」「模型不可用」或「审查失败」，不要把父线程等待到期当作拒绝理由。
4. 输出仅四块：风险等级（低/中/高/致命）；结论（通过/打回/需修改）；理由（3-5 条，每条一句话）；修改清单（优先级 + 改什么 + 怎么算改好）。
```

## 五、成本控制

1. 闸门默认关闭：日常任务、低风险写作、单文件小改、可回退操作一律不触发；
2. 每个启用任务设固定成本上限：每轮只派发 1 次；每次等待 120 秒后只做一次 `read_thread` 状态探测；连续两个快照无进展才救援一次，救援后只再等待一次；只有明确启动/模型/账户/任务失败才重试 1 次；修订重审最多 2 轮，3 次未过即熔断转人工；
3. 触发判定本身就是省成本的关键：拿不准按「看似复杂」触发一次，成本由熔断兜底，不会无限循环。

## 六、状态与回收记录

| 状态 | 含义 | 下一动作 |
|---|---|---|
| `spawned` | 已创建子代理，尚未取得运行证据 | 等待并查询状态 |
| `running` | 已开始执行或仍有进度 | 用 `read_thread` 比较最新更新时间/最近事件；有进展则继续等待，不重复派发 |
| `running_no_progress` | 连续两个 `read_thread` 快照仍运行且没有新事件、更新时间或产物增长 | 仅一次 `send_input(interrupt=true)` 救援，要求立即返回四块摘要 |
| `wait_timeout` | 本轮等待窗口结束，未收到完成/需关注事件 | 立即 `read_thread`，不直接重试、不关闭 |
| `rescue_requested` | 已发送中断式收束要求 | 只再等待一次并重新 `read_thread`；仍无终态/报告才允许关闭 |
| `completed_no_report` | 子代理已完成，但 final 未回到主线程 | 读取 `previous_status`、线程记录或落盘产物 |
| `failed_start` | 启动失败、模型不可用或账户不兼容 | 修正原因后用同一任务卡重试一次 |
| `failed` | 明确任务执行失败 | 判断是否可修正；最多重试一次 |
| `fallback` | 救援失败或重试仍失败，已确认无法回收报告 | 先 `close_agent` 终止，再由主线程按同一验收清单兜底并如实说明 |
每次交付至少记录：子代理 ID、派发时间、模型与推理档、任务卡范围、每轮等待时间、每次 `read_thread` 的状态与更新时间、是否有进展、救援动作、最终状态、报告回传来源、是否重试及理由、是否由主线程兜底。注意：`close_agent` 是终止动作，其 `previous_status` 不能代替状态读取。


## 七、自检

启用前逐条核对：是否命中闸门（含用户补触发）？高风险任务是否在动手前已审方案？审查者是否独立（非主模型自审）？是否只审不写？是否带齐任务原文 / 方案 / 约束 / 验收标准？是否执行保守与熔断规则？用户明确要求时是否无条件启用（不重新判闸门）？未命中且用户未要求却启用了 → 立即停止，按常规处理。
