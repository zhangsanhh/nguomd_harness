# BadCase 库（通用失败样本库）

> 项目通用失败资产库：记录 AI 助手在各类型任务中真实发生的失败样本（或明确预判的高风险场景），支撑「发现 → 归因 → 修复 → 回归」闭环。不限业务、不限范围，按任务处理链路分模块；后续出现新任务类型时扩模块。

## 一、定位与结构

本库为总库，三层包含关系：

- BadCase 库（本库）：通用失败样本、模块分类、修复闭环与回归集

## 二、何时记录

1. 真实失败：用户纠正、返工、双轮审查失败、回归验证失败、复盘发现；
2. 预防预判：明确可预判的高风险场景（规则变更前/任务启动前），标注为「预防型」；
3. 先查重再录入：与现有条目重合不新增；不编造案例。
4. 强制检查：每轮回复结束前执行沉淀检查（AGENTS.md 第 6 节第 1 条），命中上述任一情况即录入；无新增时回复末尾输出"📌 沉淀：本次无新增"。

## 三、任务开始前就近复用（R-06）

1. 任务开始前只检索最相关的 1—3 条 Bad Case 或 Pitfall；优先按目标对象、材料类型、交付位置和失败现象匹配。
2. 将命中案例转成当前任务的可检查条件，并在任务记录或交付说明中简记“关联案例＋检查结果”；不整库加载，不把旧结论机械套用。
3. 同类问题再次出现时沿原条目追加“复发”，不要重复建同义案例；案例适用边界变化时先标“待复核”。

## 四、单条字段与状态

基础字段：编号、模块、根因类型、场景与用户输入、实际结果、预期结果、影响与严重度、根因分析、处理方式、修复状态。

闭环字段：来源定位、事件日期、补录日期、当前处理状态、最近复发日期、最近验证日期、最近验证范围、最近验证结果与证据、关联回归项、下一动作及触发条件。

- 状态流转：待审核 → 已批准 → 执行中 → 待验证 → 已验证 → 已关闭
- `已验证`只表示注明范围内的验证通过；静态格式检查、规则写入或用户确认不能替代行为验证。证据不足时写“证据不足”，不强行改成通过。
- 复发后重新进入待审核或待验证，历史验证记录保留；用户明确不采纳可已关闭，但不计为修复成功。
- 严重度：P0（事实错误、越权、数据丢失、核心任务阻断）；P1（返工、效率严重受损）；P2（体验与轻微问题）

## 五、修复闭环（核心）

1. 录入/发现 → 归因 → Agent 提交修复建议清单 → 用户审核勾选 → Agent 执行 → 回归验证 → 沉淀复盘。
2. Agent 未经用户批准不得自行修复。
3. 每条修复建议必须附带：修复内容、影响面、风险系数、回归范围、回滚方式。

### 风险系数

| 级别 | 含义 | 示例 |
|---|---|---|
| 低 | 局部修改，影响单一模块 | 补案例、改错别字、补检索词 |
| 中 | 影响一类任务 | 修改 AGENTS.md 单条规则、调整 Pitfall 条目 |
| 高 | 影响全局或多处引用 | 移动/重命名文件、删除旧规则、改目录结构、改全局流程（执行前先列影响面与备份方案） |

### 防次生问题

- 每个修复执行前做反向校验：会不会让其他场景变差；
- 执行后跑回归集（`回归集.md`），并用 `rg` 检查所有引用路径；
- 汇报中注明验证结果与残余风险。

## 六、审计与只读校验

审计台账必须区分“机械线索”和“深审候选”：摘要关键词只用于定位，不计作失败数；深审候选须还原“原要求→首次结果→纠正或验证失败→后续处理”。每条深审候选都要有来源和去向，无法确认时保留证据不足，不补造。

`工具调用经验/闭环只读校验.py`只检查一致性，不自动修改案例状态、不删除重复条目、不修复链接。执行结果应注明检查范围、通过项、失败项、阻断项和证据不足项。
