# 一套通用的人机协作 harness

> 这不是提示词技巧合集，而是一套可以整套搬走的协作基建：**规则分层、记忆续接、失败资产、自动化护栏、成本核算**。
> 附《人机协作的迭代史》——记录这套东西是怎么被真实失败一条一条逼出来的，而不是先有架构图再落地。

## 装好它，只要三步

```bash
git clone https://github.com/zhangsanhh/nguomd_harness.git
cd nguomd_harness
./install.sh
```

`install.sh` 会自己做完剩下的事：检查依赖（node / python3）、把钩子配置里的路径改成本机绝对路径、补上脚本执行权限、建好运行时目录，然后**当场自检并把结果打给你看**——时间注入是否工作、正常命令能不能放行、危险命令拦不拦得住。看到四个 ✓，闸门就已经在跑了。

```
[4/5] 自检
  ✓ 时间注入正常：当前时间：2026-09-13 20:36（北京时间）
  ✓ 正常命令放行
  ✓ 危险命令已拦截
  ✓ 闸门工作正常
```

想装进自己的项目，加一个路径就行；只想体检、不改任何文件，用 `--check`：

```bash
./install.sh /path/to/your/project   # 装到自己的项目
./install.sh --check                 # 只自检
```

最后在客户端里点一下：Codex → Hooks 设置页 → 确认信任本项目的钩子（信任按文件内容哈希绑定，改过 `hooks.json` 后需重新确认）。钩子按 Codex 的 `.codex/hooks.json` 格式声明；其他客户端只要能执行命令式钩子也能接，把 8 条 command 按各自格式重新声明一遍即可，**脚本本身不用改**。

## 一、它解决什么问题

大多数人和 AI 的协作停在三件事上：对话结束，经验就消失；同一个坑，隔几天再踩一次；规则写在聊天里，换个会话就失效。

再往后走，会遇到四个更硬的问题：上下文被压缩后关键决策丢失，任务断链；危险操作只有一句"请注意"，而文字规则依赖执行体自觉；成本只有"感觉不贵"，没有总账口径；产出越来越多，却说不清哪条规则还有用、哪条该删。

这套 harness 就是针对这四件事搭的。它的基本假设是：**AI 的能力是可替换的，协作的规则才是资产**。所以规则不写在对话里，而写成带版本号的文件。

## 二、搭完之后是什么效果

以下都是这套 harness 跑在真实工作里的实测口径，不是设计目标。

**规则可追溯。** 主规则文件从 V1.0.0 迭代到 V1.40.0，累计 42 条变更记录。翻回来看，几乎没有一条是提前设计出来的：写操作留痕是被连续漏记六次逼出来的，压缩续接是被压缩后失忆逼出来的，危险命令闸门是差点执行危险操作之后补上的。每条变更都能对上一次真实失败。

**失败不复发。** 回归集把教训冻结成"输入 → 预期 → 状态"的检查点，改规则前先跑，失败就停止放行。失败样本库按七个模块分类，每条十个字段，状态从待审核走到已关闭。

**记忆能续接。** 压前写机械快照，压后重建任务基线并与摘要交叉校验，缺失项标"摘要缺失"而不是猜测补全。会话日志一问一答一条，倒序追加、只追加不覆盖，覆盖 44 个日期。

**危险操作拦得住。** 九条窄黑名单在命令执行前硬拦删除类、递归破坏类、权限变更类操作；配预演模式、基线回滚和定期变体绕过测试。这里有一条反面经验值得说：变体测试曾发现"删家目录、换路径调用、删除查找结果"等变体全部放行——**装过闸门不等于拦得住**，所以安全结论是组合防线，不是一张黑名单。

**成本有账。** 8 月 1—12 日累计约 106 活跃小时、约 148.5 元，折合约 1.4 元/活跃小时。8 月 17 日服务方改峰谷定价，高峰输出单价约为原价 4.5 倍，旧预算当天失效——这就是为什么每个机制都要过成本闸门四问。

**浪费能被看见。** 回放一段已完成长任务的 467 次模型调用，定位出七类浪费：日志每轮重复编辑、路径反复探索、内联脚本重写、同一话题连续搜索 23 次、规则反复改写、脚本未复用、误读凭据文件。七类问题后来逐条变成了规则。

**结构可复用。** 需求池累计 52 条，收敛成七个模块、八环节主链路、五个横切面；每个模块只做自己那一段，跨模块只传产物、不传过程。

## 三、怎么搭：两条路

**路一，直接装现成的。** 跑 `./install.sh`，上面那套规则、脚本、失败库、迭代史就全在你机器上了。适合想先看效果、再决定改哪里的人。

**路二，从零搭一套自己的。** 如果你想长出来的规则是自己的，就按下面九层走——本仓库的资产只当参照物，不要照抄。

### 九层结构：每层回答一个问题

整套 harness 分九层，递进关系是：**先想清楚 → 立规矩 → 留记忆 → 少犯错 → 兜失控 → 搭环境 → 干实活 → 向外学 → 沉淀方法**。

| 层 | 回答的问题 | 本仓库对应资产 |
| --- | --- | --- |
| 1 意图与决策 | AI 什么时候动手、什么时候问人、问什么 | `AGENTS.md` 的确认分级与需求澄清；`提示词库/需求澄清纪律.md` |
| 2 规范与指令 | AI 凭什么每次都按规矩来 | `AGENTS.md`＋`AGENTS版本变更.md`＋`回归集.md`＋`提示词库/` |
| 3 记忆与上下文 | AI 怎么记得我是谁、做过什么、到哪了 | `.codex/archive_*.py`、`.codex/pre_compact.sh`；`提示词库/压缩后跟进提示词.md` |
| 4 质量与失败 | 犯错之后怎么长记性 | `BadCase库/`（失败样本、回归集、评估集）；`提示词库/Codex借鉴-独立审查角色模板.md` |
| 5 护栏与自动化 | 自觉靠不住时怎么兜底 | `.codex/hooks.json`、`pre_tool_use_gate.sh`、`doom_loop.sh` |
| 6 环境与接入 | 体系跑在哪、花多少钱 | `.codex/config.toml`；`AGENTS.md` 的成本与权限条款 |
| 7 工具与业务应用 | 体系到底承接了什么活 | `提示词库/长文管线.md`、`提示词库/资料参照检索规则.md` |
| 8 认知进化与对标 | 什么值得学、什么该拒绝 | `AGENTS.md` 的净增量评审三标准 |
| 9 成本与能力保留 | 这套东西花得起吗、会长对吗 | `AGENTS.md` 的成本闸门四问与能力保留制度 |

### 从零起步：一天能跑起来

不要一次搭九层。按这个顺序，一天就能跑起来最小可用版本：

1. **建目录并纳入版本管理**。一个项目根目录，`git init`，先有"能回退"这件事。
2. **写第一版 `AGENTS.md`，只写三条规则**：单义任务直接执行、多解任务先列假设、不可逆操作先说明再动手。规则要带触发条件，没有触发条件的规则等于没写。
3. **加最简记忆层**：每轮对话追加一条日志（时间、摘要、主题），倒序、只追加。这一步解决"说过的话找不回"。
4. **加一道护栏**：把删除类、递归破坏类命令列成窄黑名单，在命令执行前拦。

跑一周之后，再按九层往里补。补的时候只问一句话：**这条规则解决了哪个真实痛点？** 答不上来的就删掉——规则不是越多越好，写得太多反而稀释注意力。

### 移植到自己的场景

- 装到已有项目：`./install.sh /path/to/your/project`。目标目录里若已有同名文件，脚本不会覆盖，而是写成 `xxx.harness-new` 让你自己合并。
- 已在用的 `AGENTS.md` 不要整份替换。把本仓库的规则条目挑出来追加进去即可——留下规则，换掉例子。
- 失败样本库建议从空库开始，只记录你自己真实发生的失败；参考的是字段结构和处理流程，不是别人的案例。
- 脚本靠自身位置解析路径，整目录搬到哪都能跑，不需要改脚本代码。

## 四、目录结构

```
.
├── install.sh                   一键安装与自检
├── AGENTS.md                    主规则文件（完整工作区快照）
├── AGENTS版本变更.md             42 条规则变更记录
├── 回归集.md                     改动前必跑的检查点
├── 人机协作的迭代史/
│   ├── 人机协作的迭代史（产品叙事版）.html    按七组痛点组织，适合通读
│   ├── 人机协作的迭代史（技术架构版）.md      按九层机制组织，适合检索
│   └── 维护源稿/                             产品叙事版的维护源
├── 提示词库/                     需求澄清、长文管线、独立审查、论断核验矩阵等
├── BadCase库/                    七模块失败样本、回归集、评估集、工具调用经验
└── .codex/                       会话钩子与脚本（钩子声明、归档、闸门）
```

`install.sh` 是可重复运行的：装完想复查，跑 `./install.sh --check`；就地激活会改写 `.codex/hooks.json` 的路径，用 `git checkout .codex/hooks.json` 即可还原成模板。

## 五、从哪读起

- **只想看结论**：读本文件的第二节，以及《迭代史（产品叙事版）》的总纲与第 9 章。
- **想直接抄作业**：`AGENTS.md` ＋ `提示词库/`，改写成自己的版本。
- **想理解机制怎么长出来的**：读《迭代史（技术架构版）》，它按九层展开，每层都写明解决什么失败。
- **想建自己的失败库**：读 `BadCase库/README.md` 与 `模板_单条badcase.md`，看字段与状态流转。

## 六、边界说明

**钩子按 Codex 的 `.codex/hooks.json` 格式声明。** 其他客户端只要能执行命令式钩子也能接：把 8 条 command 按各自格式重新声明一遍即可，**脚本本身不用改**。把配置放在用户目录的客户端（如 DSH），需要按它的规范另行接入。`install.sh` 在 macOS 上实测通过，Linux 下应可直接运行但未实测。

**这是方法与规则层的摘录。** `AGENTS.md` 是完整工作区的规则快照，其中提到的部分目录（个人记录、日程、设备日志等）未随本仓库发布——前者属于隐私，后者涉及版权。因此文档中会出现指向仓库外路径的引用，属正常现象。

**所有数据是本地实测口径。** 经验来自单机、单人、单一时段（2025 年末至 2026 年 8 月），量化数据不构成通用承诺。原文中标注为"部分实证"或"待验证"的机制，本仓库保留原标注，不做成品化包装。

**证据分级照原样保留。** 体系自己做过一轮双轨审核，内部证据 8 行中 7 行是"部分实证"——这份自我评价也一并保留在文档里。
