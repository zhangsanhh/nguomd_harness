# DSC：把 AI coding agent 用成一套可治理的协作体系

> 一份可复用的人机协作规则集：用需求池、规则版本、失败样本库、回归集与自动化钩子，管理人与 AI 之间的长期协作。
> 面向不写代码、但每天大量使用 AI 的人；也面向想看清"AI 产品治理"具体长什么样的产品与工程读者。

## 一、这个仓库是什么

多数人和 AI 的协作停留在一次性对话：问完即走，经验不沉淀，同样的坑反复踩。本仓库记录的是一套反过来的做法——**把协作本身当成产品来设计**。

规则从 2026 年 8 月 1 日开始体系化，到 8 月 31 日完成第三期增量：需求池累计 52 条，规则文件从 V1.0.0 迭代到 V1.40.0，累计 42 条变更记录。翻回来看，几乎没有一条规则是"先见之明"写下的——写操作留痕是被连续漏记逼出来的，压缩续接是被压缩后失忆逼出来的，危险命令闸门是差点执行危险操作之后补上的。

它不是一个软件，也不是提示词合集，而是一套跑在真实工作里的配置、规则与失败资产。

| `.codex/` | 会话钩子与脚本 | 想把规则从文字升级成机械动作 |

三条阅读路径：

1. **想快速了解全貌**：读 `02_科普指南/人机协作的迭代史/人机协作的迭代史（产品叙事版）.html`，按七组痛点讲述整套体系怎么长出来。
2. **想直接复用**：读 `AGENTS.md` 与 `提示词库/`，把规则改成自己场景的版本。
3. **想理解机制设计**：读《人机协作的迭代史（技术架构版）》与 `BadCase库/`，看每一层解决什么问题、失败如何变成规则。

## 三、核心结构速览

**七个模块**，按依赖分三档。P0 主链路必备：需求意图、工具执行、质量验收、安全兜底；P1 效率支撑：规划决策、情境记忆；P2 成长增强：成本迭代。

**八环节主链路**：需求 → 澄清 → 规划 → 上下文组装 → 执行 → 验证 → 交付 → 沉淀，每个环节都配正常与异常双轨。

**五个横切面**：安全与权限、成本与预算、记忆与连续性、质量与审计、隐私与边界。

**四层规则**：平台内置层 → 全局层 → 项目层（唯一规则来源）→ 专项层（按需触发），冲突时按权威顺序仲裁。

## 四、最值得先拿走的六条规则

1. **需求澄清纪律**：每轮最多问 2—3 个问题；必填五维是目标、范围、格式、约束、验收，缺什么问什么，非必填项进默认假设清单。
2. **决策分级**：日常操作默认执行，敏感操作需确认，不可逆操作先说明方案与影响面再动手；反复出现且答案相同的决策升级为默认值，出过错就降回确认。
3. **失败样本库**：每条记十个字段（编号、模块、根因类型、场景与输入、实际结果、预期结果、影响与严重度、根因分析、处理方式、修复状态），状态从待审核走到已关闭，录入前先查重。
4. **回归集**：把教训冻结成"输入 → 预期 → 状态"的检查点，改规则前先跑，失败就停止放行。
5. **危险命令闸门**：用窄黑名单硬拦删除类、递归破坏类、权限变更类操作，并定期做变体绕过测试——因为装过闸门不等于拦得住。
6. **成本闸门四问**：加任何机制前先答，省下了什么、返工成本多高、有没有更轻的路径、产出能不能复用。

## 五、怎么用到自己的项目

1. 把 `AGENTS.md` 复制到项目根目录，按自己的场景改写——留下规则，换掉例子。
2. 把 `.codex/hooks.json` 里的 `$PROJECT_ROOT` 替换为实际路径，并在客户端钩子管理界面重新确认信任（信任按文件内容哈希绑定）。
3. `BadCase库/` 建议从空库开始起步，只记录你自己真实发生的失败；参考的是字段与流程，不是别人的案例。
4. 规则不要一次写全。从一条开始，凡是回答不出"它解决了哪个真实痛点"的规则，就删掉。

## 六、边界说明

本仓库是完整工作区中**方法与规则层**的公开摘录。个人记录、日程、设备日志与第三方课程摘录不在其中——前者属于隐私，后者涉及版权。

所有经验来自单机、单人、单一时段（2025 年末至 2026 年 8 月），其中的量化数据均为本地实测口径，不构成通用承诺；部分机制在原文中即标注为"部分实证"或"待验证"，本仓库保留这些标注，不做成品化包装。
